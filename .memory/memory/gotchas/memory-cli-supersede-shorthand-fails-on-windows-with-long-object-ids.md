On Windows, `memory remember --stdin` auto-derives a relation's filename by concatenating both full object ids (plus the predicate), with no way to override it. Confirmed via two independent entry points that share this one root cause:

1. Supersede shorthand: the `supersede` action fails outright with `MemoryValidationFailed: File could not be written atomically` (underlying ENOENT on temp-file rename) once the derived `...-supersedes-...json` filename reaches ~290 chars. Root cause: `supersede_object` auto-creates a `supersedes` relation file named `gotcha-<long-id-A>-supersedes-gotcha-<long-id-B>.json`. Workaround: use `memory save --stdin` with a raw `update_object` patch setting `status: superseded`, `superseded_by`, and the corrected body -- this writes only the object's own sidecar, no relation file at all. Upstream bug in @aictx/memory v0.1.55 (our READ access only); tracked locally as issue #3790. Successful workaround demonstrated in PR #3789 commit b88484867d.

2. Plain relations: the `relations` action array (e.g. a `related_to` link) has the identical derivation problem. Reproduced live 2026-07-26 while recording a GitHub Actions gotcha (PR #4158): `memory remember --stdin` happily wrote `gotcha-github-actions-expressions-binds-tighter-than-so-appending-a-guard-to-an-existing-a-b-condition-needs-parentheses-related-to-constraint-pr-gate-yml-design-constraints-paths-filter-events-and-vacuous-green-traps.json` (222-char basename) without erroring in that worktree, but `py -3 scripts/ci/validate_agent_setup.py`'s `memory-filename-length` check then failed the session: 'basename exceeds 160 characters (risks Windows MAX_PATH on checkout); shorten the object/relation id. `create_relation` accepts an explicit short `id` in the patch -- pass one instead of leaving it to auto-derive from the concatenated endpoint ids; `from`/`to` keep the full descriptive ids either way.' Unlike the supersede case, this one doesn't necessarily crash `remember` itself in a short worktree path -- it is still a live Windows-checkout risk the validator exists to catch before it reaches a machine/path combination where it does crash, exactly like case 1. Workaround: skip `remember --stdin`'s `relations` array for any relation touching a long-id object; instead delete the auto-derived file (if already written) and call `memory save --stdin` directly with a structured patch's `create_relation` op plus an explicit short `id` (e.g. `rel.<short-slug>`), keeping `from`/`to` as the full descriptive object ids. Confirmed working in PR #4158.

Net: any relation between two long-id objects is at risk under `remember --stdin`, not just supersede pairs, because `remember --stdin` never lets the caller supply the relation's own id -- only its endpoints. `memory save --stdin` with an explicit relation `id` sidesteps the auto-derivation entirely and is the general fix for both entry points.
