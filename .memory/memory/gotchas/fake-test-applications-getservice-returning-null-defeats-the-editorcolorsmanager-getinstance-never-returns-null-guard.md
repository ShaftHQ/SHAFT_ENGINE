Issues #4163/#4175 guarded AssistantTranscriptView#monospacedFontFamily/currentEditorColorsSchemeOrNull only on `ApplicationManager.getApplication() == null`, on the premise EditorColorsManager.getInstance() 'throws (never returns null) once there is no live Application'. Issue #4233 (nightly Live Tools E2E, all 3 IntelliJ live-tools job groups red) proved that premise false: LiveChatToolE2ESupport's fake Application (java.lang.reflect.Proxy, LiveChatToolE2ESupport.java:432) returns null from getService() for ANY service class it doesn't explicitly stub (ShaftSettingsState/ShaftPluginExecutor only) -- including EditorColorsManager -- rather than throwing, since EditorColorsManager.getInstance() is itself just Application.getService(EditorColorsManager.class). So a live Application existing is NOT sufficient evidence EditorColorsManager.getInstance() is non-null; both call sites now null-check getInstance()'s own return value too (fix in PR #4238, regression tests AssistantTranscriptViewTest#monospacedFontFamilyFallsBackToLogicalMonospacedWhenApplicationExistsButEditorColorsManagerServiceIsUnavailable and its currentEditorColorsSchemeOrNull twin). Generalizable: any future null-guard reasoning in shaft-intellij about 'X.getInstance() throws when no Application' must be re-verified against this fake-Application-returns-null-for-unstubbed-services shape before trusting it covers 'Application exists' too.
