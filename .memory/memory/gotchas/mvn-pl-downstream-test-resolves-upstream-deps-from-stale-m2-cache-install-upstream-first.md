During implementation work on issue #4271/PR #4277 (unified locator-selection algorithm spanning shaft-capture and shaft-mcp modules), an implementing agent ran `mvn -pl shaft-mcp test-compile` and later `mvn -pl shaft-mcp test` to verify that downstream shaft-mcp tests still passed after shaft-capture behavior changes. Both times the local run reported 'clean' with no failures. However, the actual GitHub Actions CI run was RED on `Unit Tests (shaft-mcp)` with real test failures directly caused by the shaft-capture behavior change.

Root cause, confirmed when the implementing agent re-investigated: Maven's `-pl` (project list) flag without `-am` (also-make) resolves transitive dependencies from the LOCAL `~/.m2` REPOSITORY CACHE, not from the uncommitted changes in the local working tree. Since the working-tree version string (10.3.20260722) hadn't changed, Maven silently resolved the STALE, pre-#4271 cached shaft-capture jar into shaft-mcp's test classpath. This meant `mvn -pl shaft-mcp test` was testing shaft-mcp against OLD shaft-capture behavior, twice, while looking like a legitimate downstream-clean verification. `test-compile` was doubly blind to this since it can't even see behavior changes, only signature/compile changes. The working-tree changes to shaft-capture's behavior were NEVER tested locally.

Fix adopted by the implementing agent: `mvn -pl shaft-capture install -DskipTests -Dgpg.skip=true` (plain `install` alone fails locally on GPG-signing; `-Dgpg.skip=true` needed) to force a fresh install of the upstream module into the local repo BEFORE running `mvn -pl shaft-mcp test`. This reproduced the actual CI failure exactly, letting the real fix be built and verified against real behavior.

Context: The repo's Maven guard rules forbid `mvn -am test` for scoped runs to avoid running the full ~2300-test suite (see gotcha.unscoped-am-mvn-test-can-crash-the-jvm-across-the-whole-reactor). This constraint makes `-pl <module> test` (without `-am`) THE safe, guard-compliant way to verify a scoped test. However, it is EXACTLY the command that can silently mask an upstream behavior change if the upstream module hasn't been locally installed first. Anyone verifying a cross-module change in this repo needs to know to `mvn -pl <upstream-module> install -DskipTests -Dgpg.skip=true` first, or the downstream `-pl <downstream-module> test` run proves nothing about the actual change. The trap exists because the safe command and the misleading command look identical from the outside.
