When dispatching Agent tool calls with isolation:"worktree" while the task target is a DIFFERENT local repo than the one the orchestrator/main-thread session is running in (e.g. orchestrating from SHAFT_ENGINE but instructing coders to work in a separate clone like C:/Users/Mohab/IdeaProjects/selenium via an absolute path in the prompt), the isolation worktree gets created against the ORCHESTRATOR session repo (confirmed: worktreePath came back under SHAFT_ENGINE/.claude/worktrees/agent-<id>), not the target repo named in the prompt. The dispatched agents then all operate directly on the SAME shared target-repo checkout with zero real isolation, even though the tool result implies each got its own isolated copy. Caught mid-task via git status showing multiple agents' concurrent uncommitted changes; corrected by having each agent stage/commit only its own exact file paths (never git add -A/.) and avoid any git checkout/stash/reset against files it does not own (one agent independently self-caught the same risk before being told). Why: isolation:worktree has no parameter to point at an arbitrary target directory -- it isolates cwd, not an instructed path. How to apply: for any cross-repo delegation (dispatching agents against a repo other than the one the current session/orchestrator is running in), do not rely on isolation:worktree for safety. Either (a) manually create separate git worktrees of the TARGET repo yourself first and give each agent a distinct worktree path to cd into, or (b) if one shared checkout is acceptable, explicitly instruct every agent up front to stage/commit only its own exact files by path and never run destructive/blanket git commands (checkout --, stash, reset, add -A) against the shared tree.
