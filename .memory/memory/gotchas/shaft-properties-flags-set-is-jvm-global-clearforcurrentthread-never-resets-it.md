Historical gotcha, now FIXED (issue #4328, PR #4331) -- keep for context, not as a workaround-required trap. Flags.setProperty (Flags.java ~18-26) writes into the static JVM-wide Properties.baseFlags, and unlike sibling property groups had no *Override ThreadLocal for Properties.clearForCurrentThread() to remove, so a flag set in one test class silently leaked into the next test class sharing the same Surefire fork. A literal ThreadLocal mirror of the sibling pattern was considered and rejected: it would have broken the deliberate, still-active cross-OS-thread guarantee proven by testPackage.unitTests.ThreadLocalPropertiesTest#testFlagsConfigurationIsSharedAcrossThreads (Properties.java class javadoc ~19-24 documents Flags as intentionally engine-wide/cross-thread-shared during a test's execution). Actual fix: Properties.java gained a pristineBaseFlags snapshot captured once in PropertiesHelper.loadProperties() right after Properties.baseFlags is first created (PropertiesHelper.java ~96-98), and Properties.clearForCurrentThread() (~250-254) now resets Properties.baseFlags to that snapshot at test-class boundaries -- preserving cross-thread sharing during a single test while eliminating the cross-test-class leak. Regression test: FlagsSetPropertyCoverageUnitTest#testClearForCurrentThreadResetsFlagsOverrideToPristineValue. If you hit stale-flag-state symptoms in a test written before this fix, they should no longer require the old manual capture/restore-in-finally workaround -- if you still see leakage, this fix may have regressed, re-open #4328.
