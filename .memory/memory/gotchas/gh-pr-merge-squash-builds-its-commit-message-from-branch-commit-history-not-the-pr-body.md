When squash-merging with `gh pr merge --squash` (no explicit --subject/--body), GitHub composes the squash commit message from the branch's individual commit messages/subjects, not from the PR description you edited at merge time. GitHub's issue auto-close keyword scan (Closes/Fixes/Resolves #N) reads that squash commit text. A stray closing keyword left in an early commit message -- even one you later corrected only in the PR body -- will still auto-close the wrong issue on merge. Fix: before squash-merging, `git log <base>..HEAD --format=%B` and grep for closing keywords, or pass an explicit `--subject`/`--body` to `gh pr merge` that overrides the auto-generated text. Caught via issue #3708 being closed at the exact merge timestamp of PR #3710 despite the PR body deliberately avoiding the keyword.

Same trap bit again on PR #3977: editing the PR's GitHub description (`gh pr edit --body '...'`, e.g. to say 'Progresses #3965 (does NOT close it)') does NOT change this -- the branch's ORIGINAL commit message still said 'Closes #3965', so issue #3965 still auto-closed on merge and had to be reopened. `gh pr edit` only changes the PR description shown on GitHub; it never rewrites the branch's own commit text that `gh pr merge --squash` actually uses. If `--subject`/`--body` overrides aren't being passed, the only reliable fix is to change the commit text itself before merging (`git commit --amend` on the offending commit) and verify with `git show <branch-tip> --format='%s%n%n%b'` -- not `gh pr view`'s body field, which reflects the description, not the eventual squash text. See gotcha.githubs-auto-close-keyword-scan-is-negation-blind-does-not-fix-n-still-closes-n for a further nuance: even a NON-closing mention (negated, or quoted as documentation) can still trigger auto-close, so avoid any keyword+#N adjacency anywhere in the final squash text, not just avoid genuine 'Closes' intent.
