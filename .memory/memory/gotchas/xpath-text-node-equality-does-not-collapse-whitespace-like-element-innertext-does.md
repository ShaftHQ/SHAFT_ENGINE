element.innerText (used by the capture recorder's accessibleName()) reflects RENDERED text, so CSS whitespace/newline collapsing already applies. Raw DOM text nodes (what XPath's text()/. node-value sees) do NOT collapse -- they preserve literal source whitespace and newlines. An XPath predicate built with exact text equality (e.g. .="foo") against a recorded, already-collapsed name can fail to match the live DOM even though the visible text is identical, because the DOM text node still has the original multi-space/newline content. Fix: always wrap the DOM side in normalize-space() when comparing against a recorder-collapsed name (shaft-capture-recorder.js computeReplayXpath, issue #4026). Same logic applies to any other codegen that builds XPath from a recorded/rendered text value.
