Generalizable methodology lesson from the #4072 -> #4107 AssistantGeminiLiveE2ETest fix sequence (full technical detail already recorded in [[decision.running-the-live-gemini-e2e-test-for-the-intellij-plugin]] -- this entry is the distinct, reusable process lesson, not a duplicate of that one). Across successive nightly reruns of the same assertion, the reported failure text progressed: 'Provider returned malformed JSON.' -> 'Unexpected end-of-input in property name' -> 'truncated at the output-token budget (finishReason=MAX_TOKENS)'. Each intermediate fix (#4072, then #4107) was real and each one's fix made the NEXT underlying cause visible for the first time, rather than the nightly just staying red for one unchanged reason. If this run had been judged only on 'still red' at any of those checkpoints, each real fix would have looked like a failure. The generalizable rule: when triaging a recurring nightly failure across reruns, compare the actual failure signature/message between runs, not just the pass/fail bit -- a changed signature after a fix lands is a positive signal the fix worked and surfaced the next real layer, and the review should target that new signature specifically rather than reopening the old one.
