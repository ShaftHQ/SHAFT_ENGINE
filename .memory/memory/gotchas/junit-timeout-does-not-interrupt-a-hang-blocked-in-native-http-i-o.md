Reproducing #4046 in ManagedCaptureRecorderBrowserTest, a @Timeout(60) in same-thread interrupt mode failed to abort a real hang: the run was still going at 2m40s and required a manual taskkill /F /T to end it. jstack pinned the blocked thread inside RemoteWebDriver.executeScript -> JdkHttpClient.execute -> CompletableFuture.get() (called from ManagedCaptureRecorder.start, ManagedCaptureRecorder.java:151), where thread interruption does not land because the block is native/HTTP I/O, not JVM-level. The hang also leaked a surefire JVM, a chromedriver process, and nine chrome.exe children. Documented in issue #4066, which fixed the specific amplifier by bounding CaptureManager.invoke()'s executor.submit(operation).get() to a 90s DEFAULT_OPERATION_TIMEOUT with cancellation and a diagnosable error (commit e553b74fac, Fix #4066). Rule: for anything that can block in native or HTTP I/O, use an external wall-clock bound (a server-side timeout, or a CI job/step timeout that kills the process tree) -- do not rely on @Timeout alone to bound it.
