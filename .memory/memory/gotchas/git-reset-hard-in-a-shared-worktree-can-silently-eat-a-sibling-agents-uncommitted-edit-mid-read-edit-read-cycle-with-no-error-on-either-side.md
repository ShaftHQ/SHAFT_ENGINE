During #4262/#4254 work, the orchestrator ran `git fetch`/`checkout`/`reset --hard origin/main` in a worktree (SHAFT_ENGINE_main_check) that a delegate agent was still actively using for a multi-edit sequence (3 test-method edits to one file). The reset landed between two of the delegate's Read-Edit-Read steps and silently discarded one already-applied, not-yet-committed edit. Neither side got an error: the delegate's next Edit tool call just reported the file as 'modified on disk, intentional' (indistinguishable from a normal external change), and the orchestrator's reset completed with exit 0. The delegate only caught it because its first RED test run showed 1 of 3 intended assertion changes instead of 3, then re-diffed and redid the missing edit before committing. No data was permanently lost here only because the delegate happened to verify against its own expected diff count.
Generalizes the existing one-agent-per-checkout gotcha: it is not just 'don't switch branches out from under a delegate' — any hard-reset/checkout/clean in a shared worktree is unsafe the instant a delegate might be mid-edit-sequence there, even briefly, even if you intend to restore the branch ref afterward.
