Actions.java (performAction, 'get accessible name if needed' block, ~line 527-545) computes an element's accessible name purely for report/log metadata before performing the requested action. It only caught `UnsupportedCommandException | StaleElementReferenceException` around `element.getAccessibleName()`. SafariDriver has been observed (nightly e2eLocalTests.yml MacOSX_Safari_Local, 2026-07-27 run, E2ECoverageTests#elementIsHiddenShouldPass) throwing a bare `WebDriverException` ('element is not interactable'-style) for this call on a hidden element, which propagated uncaught and turned the WHOLE requested action (reported as whatever ActionType was actually running, e.g. 'Get dom attribute ... is broken') into a broken failure -- even though accessible-name is optional reporting metadata. Sibling code in the same file/failure path (ElementActionabilityDiagnostics.safeElement, used for failure diagnostics) already catches generic `RuntimeException` around the identical `getAccessibleName()` call -- this was the established, correct pattern to match. Fixed by widening the catch to `WebDriverException` (the superclass of both narrower types), which is a no-op change on Chrome/Firefox/Edge (verified: E2ECoverageTests 40/40 and ActionsCoverageUnitTest 41/41 green on real headless Chrome + mocks) and reproduced+fixed via a new deterministic Mockito unit test (`ActionsCoverageUnitTest#performActionShouldFallbackFromGenericWebDriverExceptionOnAccessibleNameToDomText`) rather than only reasoned about -- the exact CI stack trace matched exactly once reproduced locally.
