The stash reflog lives in the shared `.git` directory and is NOT per-worktree. A sibling agent working in its own worktree ran `git stash` (correctly stashed nothing -- its tree was clean) then ran `git stash pop` anyway. That `pop` took the top entry from the global stack: an unrelated, months-old entry from a completely different branch/session. It silently applied that entry's content over the agent's own working tree (corrupting an in-progress `AGENTS.md`, dropping a stray file) and, per normal `pop` semantics, dropped the entry from the stack.
`git stash pop` with nothing of your own stashed is NOT a no-op and gives no warning the entry belongs to someone else -- in a repo running many concurrent worktree-based agents, one careless `pop` destroys another session's parked work.
Recovery when this happens: re-stash the popped content immediately (`git stash push -m "<label> -- rescued, do not drop, belongs to <original owner/session>"`), then restore your own file from your own commit. Verify with `git stash list`.
Rule: never `git stash pop` / `git stash apply` speculatively. Only pop an entry you just created *and* can identify by its message -- check `git stash list` first, then pop by explicit ref (`git stash pop 'stash@{N}'`, quoted in PowerShell because of the braces). Prefer not using stash at all when worktrees are in play: commit to your own branch instead, which is per-branch and cannot collide.
