Issue #4079, fixed in PR #4106 (commit 807a2eaa5d). A guard step originally pointed at shaft-engine/target/surefire-reports/TEST-cucumberTestRunner.CucumberTests.xml, which only exists when that class is selected ALONE. The real CI job's %regex[.*CucumberTests.*] selector (.github/workflows/e2eLocalTests.yml, 'Run Cucumber tests' step, -Dtest=%regex[.*CucumberTests.*]) matches multiple classes (CucumberTests plus e.g. CucumberTestsHelperCoverageUnitTest, testPackage.properties.CucumberTests), so Surefire's TestNG provider instead writes each matched class's JUnit-style report under surefire-reports/junitreports/TEST-<Class>.xml -- confirmed by rerunning the exact job command locally and inspecting every file Surefire actually produced (see e2eLocalTests.yml comment block above the 'Verify Cucumber scenarios actually executed' step, and scripts/ci/assert_tests_executed.py's FileNotFoundError guard added in the same commit). A guard written and validated against a single-class local run will not find the report file in the real multi-match CI job -- check which shape applies before writing or debugging any surefire-reports/ path assertion. scripts/ci/assert_tests_executed.py now fails with a clear ::error:: message (not an unhandled traceback) when the expected report file is entirely absent, explicitly naming this junitreports/ possibility as the likely cause.
