Actions.java selectValue() used `!"select".equals(targetElement.getTagName())` to decide whether to use Selenium's native Select wrapper vs. SHAFT's custom non-select-dropdown fallback (click + find option 'below' via smart locator). Selenium's own `Select` constructor (selenium-support 4.46.0, verified from sources jar) uses `!"select".equalsIgnoreCase(tagName)` -- case-insensitive. SafariDriver has been observed (nightly e2eLocalTests.yml MacOSX_Safari_Local, 2026-07-27, GUIWizardTests#test_selectFromDropdownList) returning 'SELECT' (uppercase) for a verified real `<select id="dropdown">` element on a stable public page, causing SHAFT's case-sensitive check to wrongly route to the non-select-dropdown branch, which can never find a matching option for a real native dropdown -> `NoSuchElementException("No elements were found.")` thrown from `Actions.chooseBestEffortDisplayedElement`, matching the exact CI stack (down to 'Driver info: driver.version: unknown'). Fixed by switching to `equalsIgnoreCase`, matching Selenium's own established convention; zero behavior change on Chrome/Firefox/Edge (they already return lowercase 'select'). Reproduced deterministically via a new mocked unit test (ActionsCoverageUnitTest#selectActionShouldTreatUppercaseSelectTagNameAsNativeDropdown, tag name stubbed to 'SELECT') before fixing, and verified against real headless Chrome (SmartLocatorsRealisticTests 3/3, unaffected).
