When a reviewer/orchestrator re-runs the exact `bazel test` command a delegate already ran, to independently confirm its claimed pass/fail results, Bazel will often return `(cached) PASSED` for every target instead of genuinely re-executing them against the current tree. A cache hit is not evidence that the target was exercised against the diff you're currently reviewing -- it just means the same inputs produced this cached result at some point. Force a real re-execution with `bazel test --nocache_test_results <targets>`, then additionally pull the JUnit XML per target to confirm the *specific* new/renamed test case names are present with 0 failures, not just a suite-level green. Discovered during the Selenium PR #17832 round-2 review (commit 609c6e2140): a hostile-reviewer agent's first verification pass silently accepted a cached green before catching itself and re-running with --nocache_test_results.
