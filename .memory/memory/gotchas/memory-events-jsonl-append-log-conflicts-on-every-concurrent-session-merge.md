`.memory/events.jsonl` is an append-only JSON-Lines event log -- every `memory remember`/`memory save` call appends new lines to it. Since this repo is worked on by multiple concurrent Claude Code sessions/worktrees (see constraint.worktree-housekeeping-at-session-start), two branches that both wrote memory events since a common ancestor will touch this exact file when one is merged/rebased onto the other, even though neither branch's actual intent conflicts.

Local resolution is automatic, not manual: `.gitattributes:5` declares `.memory/events.jsonl merge=union` (added 2026-07-18, confirmed via `git check-attr merge .memory/events.jsonl` -> `union`). Verified directly in a disposable test repo: a real `git merge` of two branches that each appended a different line to a common-ancestor file resolves with `Auto-merging .memory/events.jsonl`, exit 0, zero conflict markers, and the result contains BOTH sides' new lines plus the base line -- git's built-in union driver, no repo-side `merge.union.driver` config needed (`git config --get merge.union.driver` returns nothing in this repo, confirmed exit 1/not-found). Do not hand-resolve conflict markers in this file going forward; if a rebase/merge ever leaves them, the attribute has stopped applying (e.g. missing `.gitattributes`, wrong path casing) rather than there being a real content conflict. If markers do appear, keep BOTH sides' lines -- never drop either; line order does not affect correctness, `memory check`/`memory rebuild` only require each line to be valid JSON.

GitHub's server-side mergeability check does NOT reach the same answer: it flags PRs `CONFLICTING`/`DIRTY` on this file alone even when a local rebase resolves it with zero manual edits, because GitHub's precheck does not evaluate custom merge drivers. Confirmed on three real PRs in one session (#4132, #4134, #4136 -- see issue #4137, closed) and now documented in `AGENTS.md`'s New Task Flow as of PR #4149 (merged 2026-07-26T16:01:34Z, commit 8cd32d7054 on origin/main): a `.memory/events.jsonl`-only CONFLICTING/DIRTY status is a known false positive, safe to resolve by rebase+push with no manual edits -- not a reason to gitignore or untrack the file.

Separately, the file's *presence* is a hard requirement of the `memory` CLI, independent of the conflict behavior above -- its content is not. Verified in a disposable copy of `.memory/` (never the tracked store): `validateRequiredStorage` requires the literal path `.memory/events.jsonl` alongside `config.json`/`memory/`/`relations/`/`schema/` (`main.js:3652-3659`; `requireFile` errors `CanonicalFileMissing` on ENOENT at `:3661-3669`); `readEvents` (`:4482-4489`) tolerates an empty file (`contents.data === ""` -> `ok([])`) but not a missing one. Reproduced directly on a disposable copy: deleting the file makes `memory check` exit 1 with `CanonicalFileMissing`; `memory load`/`memory inspect` exit 1 with the misleading `MemoryValidationFailed: File could not be read as valid UTF-8` (the real cause is the missing file, not an encoding problem); truncating it to 0 bytes instead makes all three commands pass identically to full history (`memory check` prints `Memory check passed.`, exit 0). Only the write path (`appendJsonl`, `:183-213`, opened with `O_APPEND|O_CREAT`) auto-recreates a missing file -- a fresh `git worktree add`/clone that never calls a write command starts with whatever was last committed, so untracking or gitignoring this file would leave it genuinely missing after every future fresh checkout, breaking the mandatory session-start `memory load "<task>"` step (`AGENTS.md` New Task Flow) until some other write recreated it. That is why PR #4149 kept the file tracked and merge=union'd rather than gitignoring it, despite the GitHub-side rebase tax documented above.
