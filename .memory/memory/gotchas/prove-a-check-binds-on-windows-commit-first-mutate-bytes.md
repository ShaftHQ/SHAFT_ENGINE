The lens's `Proving a check binds` prescribes: apply the mutation to the shipped artifact, run it, read the failure, revert. On Windows two mechanical traps turn that loop into lost work or a false verdict, and both hit inside one session on PR #4524.

1. `git checkout -- <path>` is the obvious revert and it discards **uncommitted** work in that path, not just the mutation. Reverting a mutated `tests/scripts/test_agent_router_contract.py` wiped an entire uncommitted round of review fixes that happened to live in the same file, and separately wiped an uncommitted one-line change to `scripts/ci/agent_guidance_budget.json`. Commit the real work before the mutation loop starts, or copy the file to a scratch path and restore from the copy. `git status --porcelain` after the revert only proves the file matches HEAD -- which is exactly what the failure looks like.

2. Tracked guidance is CRLF on disk in this repo (`.agents/skills/act-as-mohab/SKILL.md` reads `crlf=True`). A PowerShell here-string or `(Get-Content -Raw).Replace(...)` whose pattern spans lines is written with LF, so it silently matches nothing and the mutation never lands -- the check then looks like it survived. No error is raised, and `git diff --stat` still shows whatever else was already modified, which reads as success. Mutate with Python instead: read bytes, `decode().replace('\r\n', '\n')`, transform, re-encode with the original line ending, and print the post-mutation state (the numbering, the marker list, whether the deleted text is still present) so the mutation is proved to have landed before any verdict is recorded. `Path.write_text` is not safe either: with `newline=None` it rewrites every LF as CRLF.

The rule both share: a mutation that did not apply and a check that did not fire are indistinguishable from the exit code alone. Print the artifact's mutated state, not just the test result.
