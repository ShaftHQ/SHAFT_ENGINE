RESOLVED by issue #4341: ElementActionsHelper.failAction (the failure path used by TouchActions gestures like tap/doubleTap/longTap/swipe, plus ElementActions' table-locator lookup, AlertActions, and BrowserActions' mobile-context methods) used to route through Assertions.fail, throwing AssertionError -- unlike Actions.performAction's reportBroken path, which throws RuntimeException for the equivalent browser-action failure. Fix: failAction now throws new RuntimeException(message, rootCauseException[0]) (message already carries the "Root cause: ..." text built by reportActionResult), preserving the full cause chain -- every failAction call site is a broken/failed-action report, never a genuine assertion, so AssertionError stays reserved for real assertion/validation-style checks (e.g. com.shaft.validation.accessibility.AccessibilityActions, RequestBuilder's status-code check, HttpContractRecorder's ASSERT-mode contract diff, ValidationsHelper's hard-assert path -- audited whole-engine plus every shaft-* module's src/main for Assertions.fail(/Assert.fail(/throw new AssertionError/AssertionFailedError and confirmed these are the only other hits, all genuine expected-vs-actual assertions, none touched). Fallout fixed in the same change: TouchMultipleElementsFailureTest's assertion tightened from Throwable back to RuntimeException (matching MultipleElementsFailureTest); BrowserActionsCoverageUnitTest's getContext/setContext/getContextHandles-on-non-mobile-driver assertions got the same AssertionError-to-RuntimeException tightening (that test class's other assertions were already RuntimeException-typed, confirming RuntimeException was already the norm everywhere except this one shared method); and TouchActions.swipeElementIntoView(By,String,SwipeDirection)'s inner catch block, which used to catch AssertionError specifically to bubble an already-reported failure straight to the outer wrapper without re-reporting it, now catches RuntimeException instead -- otherwise the exception fell into the generic Exception handler and got redundantly re-reported/re-wrapped an extra time (confirmed via a new mocked-failAction-overload-count regression test, AndroidTouchActionsCoverageUnitTest#visualSwipeBubblesAlreadyReportedFailureWithoutDoubleWrapping).
