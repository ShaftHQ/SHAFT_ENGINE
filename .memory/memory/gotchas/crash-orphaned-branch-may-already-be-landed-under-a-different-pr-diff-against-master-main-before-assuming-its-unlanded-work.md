A local-only branch `ChaosEngine/docs-sync-tool-sweep-3873` in shafthq.github.io looked like real orphaned crash-session work (one commit ahead of origin/master, no PR found via `gh pr list --head`). It was actually a stale duplicate: another parallel/earlier crashed session had already landed byte-identical content via PR #881 (merged 2026-07-20). `git diff <orphaned-branch-tip> <the-already-merged-commit>` on the relevant file scope showed 0 lines of difference. Opening a PR from the orphaned branch would have regressed later work (PRs #893/#895 had since moved master further on an overlapping file). Why: two agents can independently work the same subtask/issue across different crashed sessions; only one's output lands, and the other's branch is left looking orphaned even though its content already shipped. How to apply: before pushing/opening a PR from any branch found via worktree/branch housekeeping that looks unmerged (no `gh pr list --head` hit), diff its tip against current main/master for the same file/module scope first -- if the diff is empty (or only trails behind due to later unrelated work), the branch is a stale duplicate to delete, not new work to land.

Sharpened 2026-08-04 while clearing the seven branches in issue #4450, where both obvious shortcuts were wrong in opposite directions. A merged PR does not clear a branch: `shaft-skills-distribution-4350` had #4366 merged and #4369 closed-unmerged off the same branch, and still holds `skills-lock.json` and `.github/workflows/validate-shaft-skills.yml`, which exist nowhere on main. A closed PR does not condemn one either: `harness-abandoned-worktree-guard-4437`'s #4439 was closed, yet its content had landed via #4446. An empty tip diff is also too strict once main moves on -- 5 of those 6 branches had a non-empty diff against main and were all fully landed, because main had evolved the same files past them. The test that actually worked: list the files the branch touched against its merge-base, then ask which of those paths exist nowhere on main's tip; for each of those, `git log origin/main -- <path>` says whether main once had it and deliberately removed it (landed, then consolidated -- safe) or never saw it (genuinely unlanded -- keep the branch). That is local, needs no API call, and is the only check that got all seven right.
