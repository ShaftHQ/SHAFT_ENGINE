PollingBrowserEventCollector.poll() (shaft-capture/src/main/java/com/shaft/capture/collector/PollingBrowserEventCollector.java:197) literally assigns its signals' browsingContextId from driver.getWindowHandle() directly; BidiBrowserEventCollector's BiDi browsingContextId is Selenium's Chromium CDP-target-id-backed equivalent of that same handle. Both collectors deliver signals on their own listener/polling threads, never on the CDP Fetch.requestPaused callback thread used by CaptureNetworkRecorder. So ManagedCaptureRecorder.acceptSignal() can passively cache the last-seen non-blank, non-loopback browsingContextId as the current window handle (issue #4090's fix for #4077's stale-handle trade-off) without ever calling driver.getWindowHandle() from the network-interception callback thread -- avoiding #4077's reentrant-WebDriver-call deadlock entirely. Ignore BrowserEventSink.LOOPBACK_BROWSING_CONTEXT_ID (loopback) the same way CaptureEventPipeline.resolveBrowsingContextId() already does, so a redundant-channel delivery race never overwrites a real handle with the sentinel.
