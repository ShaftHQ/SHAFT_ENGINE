UPDATED 2026-07-26 after re-investigating a fresh #4005 report ('py -3 scripts/ci/validate_agent_setup.py fails on every branch'). Verdict: this is NOT a distinct content_hash/sha256 false positive (that hypothesis, from the original issue body, was already refuted in the #4005 thread -- content_hash only ever trips the non-blocking high_entropy_string WARN rule, confirmed again this round: the sha256 hex string contains no matching substring at all). It is also NOT the global npm install's patch being silently reverted by an npm update -- that patch (anchoring the openai_api_key pattern with a leading word-boundary, C:\Users\Mohab\AppData\Roaming\npm\node_modules\@aictx\memory\dist\cli\main.js:3223) was confirmed STILL INTACT and working (`memory check` on PATH passes clean, 0 MemorySecretDetected errors).

The real mechanism: scripts/ci/validate_agent_setup.py does not call the `memory` binary on PATH. It shells out (scripts/ci/validate_agent_setup.py:263-278) to `npx --yes --package <MEMORY_PACKAGE> -- memory check`, where MEMORY_PACKAGE is pinned at scripts/ci/validate_agent_setup.py:30 to the exact latest published release. npx resolves and caches that package into its OWN cache directory (`%LOCALAPPDATA%\npm-cache\_npx\<hash>\node_modules\@aictx\memory`, confirmed a distinct folder from the global npm install, keyed by the exact `--package` spec used), fetched fresh from the npm registry. That copy was NEVER patched -- the original manual fix was only ever applied to the global npm-root install. Confirmed by diffing both copies' openai_api_key rule source: global install has the leading-boundary anchor (patched); the matching npx-cache copy did not (unpatched) and hard-failed on the same body_path field as the original bug -- `.memory/memory/gotchas/worktree-isolated-agents-can-be-reclaimed-mid-task-while-still-actively-working-with-no-committed-diff.json:2`, the pattern matching mid-word inside the ordinary hyphenated word in that filename's slug (see prior write-up in this same entry / the #4005 thread for the exact substring). Checked the npm registry directly: the pinned version is still the latest published @aictx/memory release, so there is no newer pin to bump to -- the upstream release with the fix does not exist yet.

Action taken this round (machine-local only, same fragility class as the original patch): backed up the npx-cache copy first (backup file left alongside the original, named main.js.orig-npxcache-backup-2026-07-26, same directory) and applied the identical leading-boundary anchor to it. Confirmed `py -3 scripts/ci/validate_agent_setup.py` now passes ('Agent setup is valid...') after this second patch. This is EVEN MORE fragile than the original global-install patch: it lives in npx's per-exact-version cache entry, which npm/npx can evict or refetch (e.g. `npm cache clean`, a different resolved hash directory, or a future npx version). It also does NOT help any other machine or CI runner -- GitHub Actions and any fresh clone/agent start with an empty npx cache and will re-download the unpatched release from the registry, so `validate_agent_setup.py`'s memory-check step is still broken in CI and on any machine that hasn't been manually patched. There is no available in-repo code fix without an architectural decision on how scripts/ci/validate_agent_setup.py should invoke the memory CLI (e.g. drop npx and call the PATH-resolved `memory` binary instead, accepting version-drift risk, vs. vendoring a patched copy, vs. waiting for the upstream release) -- flagged to the orchestrator rather than decided here.
