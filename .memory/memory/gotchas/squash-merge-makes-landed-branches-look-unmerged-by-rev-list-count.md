`git rev-list --count origin/main..<branch>` returns non-zero for branches whose work is fully landed, because squash-merge rewrites the commits -- the branch's own commits never appear in main's history. In one session 20 of 21 worktree branches looked unmerged by that test and all but one were already on main. `git diff origin/main <branch>` is worse than useless on a stale branch: it renders main's newer commits as deletions on the branch side, which reads like the branch is about to delete live work.
Reliable check instead: whether the tracked issue is closed, plus the squash commit on main (`git log --oneline origin/main | Select-String <issue-number>`). Verify actual content with `git show origin/main:<path>` to confirm the change really landed. See also [[rebasing-a-stacked-branch-after-its-shared-history-was-squash-merged-use-onto-with-the-last-shared-commit]] for the related rebase-side pitfall.
