Issue #4037, fixed in PR #4104. Confirmed live at DriverFactoryHelper.java:713-728 (augmentRemoteWebDriver, DriverFactoryHelper.java:728-741). org.openqa.selenium.remote.Augmenter#augment captures `ExecuteMethod executeMethod = new RemoteExecuteMethod(remote)` from the driver BEFORE the ByteBuddy subclass implementing HasDevTools exists. AddHasAuthentication's own register() handler checks `((RemoteExecuteMethod) executeMethod).getWrappedDriver() instanceof HasDevTools`, and getWrappedDriver() always returns that ORIGINAL pre-augmentation RemoteWebDriver, which never implements HasDevTools -- so the check is deterministically false regardless of real session capabilities, whenever AddHasAuthentication is pre-registered alongside another augmentation (e.g. BiDiProvider) in the SAME .augment() call. Symptom: basic auth silently no-ops on remote/Grid sessions even though the CDP endpoint is perfectly reachable. Selenium's own Augmenter#addDependentAugmentations runs a SEPARATE LATER .augment() pass using the already-partially-augmented driver, so its own RemoteExecuteMethod correctly observes HasDevTools -- this is why the fix is to NOT manually pre-register AddHasAuthentication at all and let that safety net do it. Confirmed empirically via DriverFactoryHelperAugmentationUnitTest#nativeAuthHandlerShouldAttemptCdpConnectionRatherThanSilentlyNoOp. Diagnostic logging added at DriverFactoryHelper.java:734-739 (logs post-augmentation HasAuthentication/HasDevTools booleans at DEBUG).
