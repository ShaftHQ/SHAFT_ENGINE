This test (reproduces issue #3795, fixed by PR #3796 on 2026-07-20/21) mocks WebDriver/WebElement/TakesScreenshot to force both the AI-highlight screenshot path (element.getRect() -> StaleElementReferenceException) and the viewport-fallback screenshot path (driver.getScreenshotAs -> WebDriverException) to fail. In practice, on a machine with a real display (e.g. this Windows dev box), Actions.takeScreenshot()'s Screenshots.FULL branch calls ScreenshotHelper.makeFullScreenshot() BEFORE ever reaching the mocked driver.getScreenshotAs() fallback, and that manual path uses a real java.awt.Robot-based screen capture that succeeds against the actual desktop -- meaning the mocked getScreenshotAs() exception is never actually exercised locally. This did NOT affect the test's specific assertion in this case (the suppressed-exception attachment for the getRect() failure happens unconditionally before the screenshot-type branching is reached), and the test passed deterministically across 4 local runs on current main with the #3796 fix in place -- so the nightly CI failure captured for this test (run 30237601576, 2026-07-27, six days after the #3796 fix landed) could not be reproduced and no code change was made for it. Still, this is a real test-hygiene gap worth remembering: a 'pure Mockito unit test' in this codebase can silently exercise real OS-level screenshot capture on machines with a live display, which is surprising and worth checking first in any future investigation of this test's behavior.
