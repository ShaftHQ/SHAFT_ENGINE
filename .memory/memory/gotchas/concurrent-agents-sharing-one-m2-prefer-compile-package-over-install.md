Multiple SHAFT_ENGINE agents in separate git worktrees still share one local .m2 repository. A sibling agent running `mvn install` can briefly leave another agent's build reading an inconsistent installed jar/pom -- e.g. one agent's `mvn -pl shaft-engine` (without -am) hit an unresolved `${appium.flutterfinder.version}` property that did not appear anywhere in that agent's own checked-out poms, consistent with Maven resolving the parent POM from a sibling's mid-edit .m2 install rather than from local source (observed during today's concurrent flutterfinder-removal work, PR #4049 and worktree fix-4016-deprecate-flutterfinder). Note: a separately-observed postgresql 42.7.11-vs-42.7.13 mismatch turned out NOT to be .m2 cache staleness -- it was shaft-mcp's own dependencyManagement BOM-import ordering silently beating the reactor pin, already covered by gotcha.shaft-mcp-bom-import-ordering-beats-reactor-pins (PR #4019); don't re-attribute that class of mismatch to this gotcha. Operating guidance: prefer `compile`/`test-compile`/`package` over `install` in parallel-agent sessions to avoid touching the shared cache, and when a resolution result contradicts the committed pom, check BOM-import ordering and rule out a stale .m2 artifact from a concurrent sibling build before treating it as a real dependency defect.
