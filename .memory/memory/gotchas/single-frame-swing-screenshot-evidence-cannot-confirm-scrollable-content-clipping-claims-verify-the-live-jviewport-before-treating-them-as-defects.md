An area B shaft-intellij plugin audit reported, at medium confidence from a static render, that the first-run welcome bubble clipped its "Got it" dismiss button at narrow widths (issue #4163, filed with an explicit live-scroll caveat). A live Swing reachability test driving the same 360x780 DarculaLaf construction and inspecting the real JViewport/JScrollBar model (rather than re-reading the rendered PNG) showed the button fully inside the initial unscrolled viewport -- the finding did not reproduce (PR #4176).

Lesson: a rendered frame from ShaftPluginScreenshotRendererTest (or any single-shot Swing screenshot harness) shows only what is painted in the visible region at capture time, not what is reachable by scrolling. Any clipping/truncation claim about scrollable content needs a live viewport check (drive the same construction and inspect JViewport.getViewRect() / the JScrollBar model, or actually scroll) before it is treated as a confirmed defect -- this repo's plugin audits lean heavily on the screenshot renderer, so this recurs.

Flip side, worth keeping in view so the static evidence isn't discounted wholesale: the same investigation found a genuine, distinct truncation bug in the same welcome bubble at narrow widths -- the trailing paragraph text was actually cut off, not the button (filed as issue #4174). So the static screenshot evidence was not worthless; it correctly flagged that something in that component was clipped at that width, it just misidentified which element. Treat a single-frame screenshot finding as "investigate this region," not "the described element is broken" -- verify what is actually cut off with a live check before deciding what to fix.
