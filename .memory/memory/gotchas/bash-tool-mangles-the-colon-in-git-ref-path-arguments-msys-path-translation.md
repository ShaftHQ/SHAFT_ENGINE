Running a git command with a `ref:path` colon argument (e.g. `git show origin/main:.github/workflows/e2eTests.yml`, same shape for `git cat-file -p`) through the Bash tool silently rewrites the argument via MSYS path translation before git ever sees it: the colon becomes a semicolon and both forward slashes become backslashes. Observed directly this session: `git show origin/main:.github/workflows/e2eTests.yml` run via the Bash tool fails with `fatal: ambiguous argument 'origin\main;.github\workflows\e2eTests.yml': unknown revision or path not in the working tree.` -- git's error gives no hint the argument was rewritten in transit; it reads like a bad ref or missing path, not a shell/tool bug. Workaround used by the original delegate: redirect the command's stdout to a file and grep/read that file rather than parsing terminal output for a colon-bearing arg. Better fix, verified this session: run the identical command through the PowerShell tool instead of Bash -- it passed `origin/main:.github/workflows/e2eTests.yml` through unmodified and returned the full file (920 lines, exit success) with no rewriting at all. Prefer the PowerShell tool for any git command containing a `ref:path`-style colon argument; reserve the Bash tool for git commands whose arguments are plain forward-slash paths.
