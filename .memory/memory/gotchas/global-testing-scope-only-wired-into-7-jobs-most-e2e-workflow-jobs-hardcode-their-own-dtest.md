Corrected 2026-07-26 (#4086): an earlier draft of this entry concluded GLOBAL_TESTING_SCOPE was 'inert/unused' because grepping pom.xml and Java sources for it returns nothing -- that conclusion was WRONG and was caught before being recorded. It IS consumed, just not from Java/Maven: GLOBAL_TESTING_SCOPE is a workflow-level env var (defined .github/workflows/e2eTests.yml:42, a long `!%regex[...]` exclusion list; also .github/workflows/e2eLocalTests.yml:16) that GitHub Actions' shell interpolates directly into the Maven test selector inside each job's `run:` block: `-Dtest=${GLOBAL_TESTING_SCOPE}` at e2eTests.yml:248,285,322 (the Grid firefox/chrome/MicrosoftEdge jobs) and `-Dtest=${{ env.GLOBAL_TESTING_SCOPE }}` at e2eLocalTests.yml:72,103,138,314. It is the exclusion selector that keeps DB/API/mobile/Cucumber/unit-test classes out of those 7 desktop/Grid browser-matrix jobs -- genuinely load-bearing; deleting it as 'unused' would silently change what those jobs run. It is also referenced in a comment at pr-gate.yml:287 explaining why certain unit-test classes were moved out of the Grid jobs' scope specifically because of this selector. Every OTHER job in both workflow files (Sikuli, WindowsDesktopAppiumE2ETest, the Cucumber job, DB/API/Visual/Video jobs, all 5 Playwright-per-browser jobs, all BrowserStack jobs, the Cucumber-remote job, and the final Junit*,MoonTests job) hardcodes its own literal -Dtest string and genuinely never references GLOBAL_TESTING_SCOPE -- that part of the original observation still holds. The generalizable lesson (the actually durable one): an env var consumed purely through shell interpolation inside a CI workflow's `run:` step is invisible to source-level greps (pom.xml, Java, any IDE find-usages) -- 'not referenced in code' is not evidence of 'unused' for anything defined in .github/workflows/. Search the workflow YAML itself (`grep -rn <NAME> .github/workflows/`) before concluding a CI-defined env var, matrix value, or workflow input is dead.
