In GitHub Actions `if:` expressions, `&&` binds tighter than `||`. Taking an existing job condition `A || B` and appending a guard to get `A || B && github.event.action != 'edited'` does NOT gate the whole condition -- it parses as `A || (B && github.event.action != 'edited')`, leaving the `A` path ungated and silently defeating the intended skip. The correct form parenthesizes the original condition: `(A || B) && github.event.action != 'edited'`. Confirmed live in `.github/workflows/pr-gate.yml` on PR #4157 (`gh pr diff 4157`, issue 4145): every heavy leg (docs-boundary, installer-verify, intellij-build, cli, capture-e2e, unit-tests, template-coupling, workflow-timeouts, orphaned-suite-files) ships the parenthesized form `(needs.changes.outputs.X == 'true' || needs.changes.outputs.infra == 'true') && github.event.action != 'edited'` -- a delegate caught and fixed the naive unparenthesized version in its own first pass, before it shipped. GitHub's own expressions doc (docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/evaluate-expressions-in-workflows-and-actions, fetched live 2026-07-26) does not state operator precedence in prose anywhere on the page -- its operators table just lists `!`, `<`, `<=`, `>`, `>=`, `==`, `!=`, `&&`, `||` in that order, consistent with (but not an explicit textual statement of) && binding tighter than ||; the precedence must be verified empirically or trusted from the shipped, working expression rather than looked up directly. Since `.github/workflows/pr-gate.yml` is the sole required status check on main (ruleset 'PR Gate Summary'), a silently-ineffective gate on a heavy leg is invisible in a green CI run: the job just runs when it should have skipped, or the inverse shape produces a vacuous pass. Always wrap a pre-existing `A || B` condition in parentheses before appending an `&&` guard clause to it.
