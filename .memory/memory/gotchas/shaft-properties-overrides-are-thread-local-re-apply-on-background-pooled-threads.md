SHAFT.Properties.java:12-17 documents that mutable driver/session config (Web, Mobile, Platform, etc.) is stored per-thread via ThreadLocal fields (Properties.java:59-70, e.g. browserStackOverride, platformOverride). Calling SHAFT.Properties.web.set().targetBrowserName(...) only updates the calling thread's override; other threads keep reading their own override or the global base config. A test that hands work to a background thread or a pooled executor without re-applying the same overrides on that thread silently falls back to framework defaults. The failure is deceptive: the background thread just takes a different branch, the test still passes most runs, and the flake presents as a timing or HTTP problem rather than a configuration one -- ruled out empirically across 100+ runs before the thread-local mechanism was identified (#4040, PR #4051). How to apply: when a unit test spawns a thread/executor and depends on a Properties override, re-apply the same .set() calls at the top of that thread's Runnable/Callable, or restructure to avoid crossing threads.
