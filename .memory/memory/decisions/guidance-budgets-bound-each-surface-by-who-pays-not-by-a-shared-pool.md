Issue #4458 asked whether to re-arm the global total-guidance ratchet that #3745 retired. Decided in PR #4475 to leave it retired, and to cap the previously unmetered on-demand reference surface per file instead. `file_budgets` keys may now be globs, and `.agents/skills/act-as-mohab/references/**/*.md` is capped at 16384 LF-normalized bytes per file.

The rationale is incentive locality. It is a claim about authorship behaviour, not about bytes loaded, and it asks one question -- who bears the cost when a ceiling binds. Under a shared pool the bearer is whoever wrote the neighbouring file, because the only way to fund one file's growth is deleting an unrelated file's prose, and that deletion lowers nothing any session loads, since the neighbour was never in it. Under a per-file cap the bearer is whoever wrote the file that grew. Preferring the second needs no load argument, and none should be offered.

What the cap does is bound the worst single file, and nothing else. It does not bound a session total. Thirty-one files match the glob today, so the ceiling permits 507904 bytes against 92938 actually in use, which leaves growth by file count, or by many files growing at once, entirely unmetered. Only `work-github-playbook.md` is anywhere near its own cap, at 14838 bytes or 91 percent of it, and the next largest sits at 46 percent.

Do not re-derive this decision from a load argument. Two separate causal claims about load were offered in support of it, this repository's own structure refuted both, and the conclusion survived each time, which is the tell that it never rested on either. The first claim, that routing sends a task to one reference so the per-task cost is the largest single file, is false on this repository's own structure -- lines 14 to 16 of `references/routing.md` and line 200 of `SKILL.md` tell every dispatch to read both `delegation.md` and `roles.md`, and a realistic dispatch loads roughly 28639 bytes. The second claim, that a capped file's remedy is splitting and that splitting lowers real load, is equally false -- line 107 of `work-github-playbook.md` records that this split already happened in #4462 and produced a pointer to a reference every dispatch loads anyway, so load was relocated rather than reduced. Splitting also carries a perverse edge, since each half is then independently entitled to the full ceiling, which is the growth-by-file-count vector the cap is already blind to.

The empirical half stands on its own. The per-surface caps from #3745 have never been renegotiated, while the pooled floor that directive retired was renegotiated three times in one week, from 68 to 55 to 53 percent, and at one point forced deleting good prose over 21 bytes.

One tension a future reader will hit cold when re-reading #3745. Item 2 of that closed directive designated on-demand `references/` as the uncounted relief valve for a skill body that outgrows its own cap, and that surface is counted now. The valve stays functionally open, because the new ceiling is per file and sits far above anything a relocated skill body would reach.

Issue #4452 re-litigated #3745 once already, which is how #4458 came to exist, and is why this is written down.
