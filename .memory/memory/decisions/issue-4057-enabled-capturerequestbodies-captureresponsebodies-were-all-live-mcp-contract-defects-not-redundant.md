ManagedCaptureRecorder.translateNetworkCaptureOptions (shaft-capture) converted com.shaft.capture.runtime.NetworkCaptureOptions (MCP-bound, mutable) into com.shaft.capture.network.NetworkCaptureOptions (internal record) and silently dropped enabled/captureRequestBodies/captureResponseBodies -- the record had no equivalent fields. #4014's carve-out theorized 'enabled' was redundant because resolvedNetworkCaptureOptions() only runs once capture is already enabled. That theory was WRONG: apiCaptureEnabled() (ManagedCaptureRecorder.java) gates on the top-level CaptureStartOptions.apiCapture flag or the global SHAFT.Properties.capture.enabled() property -- networkOptions.enabled itself was never consulted, so a caller setting networkOptions.enabled=false while apiCapture=true had zero effect and was silently ignored. captureRequestBodies/captureResponseBodies were worse: CaptureNetworkRecorder.recordIfAccepted unconditionally stored both bodies (subject only to maxBodyBytes truncation) with no flag to gate it at all -- and shaft-intellij's RecordApiWebAction.java/GuidedWorkflowPanel.java already send both fields believing (per RecordApiWebAction's own comment) they control 'the entire point of API recording'. Fix (PR #4064): added captureRequestBodies/captureResponseBodies as new record components on network.NetworkCaptureOptions with a 6-arg compatibility constructor defaulting both to true (preserves every existing internal caller's unconditional-capture behavior with zero call-site changes); CaptureNetworkRecorder now gates NetworkBodyStore.store calls on those flags, using the existing null-BodyRef sentinel for 'no body'; ManagedCaptureRecorder gained a package-private static networkCaptureExplicitlyDisabled(NetworkCaptureOptions) consulted in startNetworkRecorder before apiCaptureEnabled()'s decision is allowed to construct a recorder, since 'enabled' has no record-side equivalent to carry through translateNetworkCaptureOptions.
