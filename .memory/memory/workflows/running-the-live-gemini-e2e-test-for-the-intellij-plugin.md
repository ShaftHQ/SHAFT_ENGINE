The installed shaft-mcp args file pins -Dshaft.mcp.workspaceRoot to %LOCALAPPDATA%/ShaftHQ/shaft-mcp/work, and the system property beats the SHAFT_MCP_WORKSPACE_ROOT env var -- pass that work dir as workspaceRoot (or scope the args file like ShaftMcpProjectScope does) or the MCP rejects 'Autobot working directory is outside the MCP workspace'. Every shaft.intellij.* test property must be explicitly forwarded in shaft-intellij/build.gradle.kts's test { systemProperty(...) } -- unforwarded -D flags silently fall back to defaults inside the test JVM. Google load-sheds gemini-3.5-flash structured-output (responseSchema) calls with 503 'high demand' while trivial payloads/model-list calls return 200; use gemini-2.5-flash for deterministic-ish live runs and expect occasional retries anyway. INVALID_RESPONSE with fallbackReason 'Provider returned malformed JSON.' is NOT only a too-small maxOutputTokens budget (raised to 8k in PR #3371, AutobotService.runProviderChat) -- issue #4072 root-caused it to GeminiProvider.parseStructuredPayload (shaft-ai) reading candidates[0].content.parts[0].text unconditionally; thinking-enabled models (gemini-2.5/3.5-flash) can emit a leading {"thought": true, ...} part before the real answer part, or exhaust the output budget on thinking before ever emitting an answer part, and the old code misread the former as malformed JSON and gave no signal for the latter. Fixed by skipping thought parts and surfacing the candidate's finishReason (e.g. MAX_TOKENS) when no usable answer part remains -- the budget theory alone could not explain the intermittency, since a leading thought part fails regardless of budget size. Follow-up issue #4107 found a THIRD variant #4072's fix didn't cover: a real (non-thought) answer part CAN exist but be incomplete -- the output budget runs out mid-generation, so the part parses fine up to the cut then Jackson throws its own raw message (e.g. 'Unexpected end-of-input in property name'), confirmed against the nightly's actual failing payload (run 30203545339). The old code let that raw JacksonException escape unchanged, indistinguishable from a genuinely malformed payload. Fixed in GeminiProvider.parseStructuredPayload by wrapping the JSON.readTree(text) call in a try/catch: only when the candidate's own finishReason equals MAX_TOKENS is the raw parse error replaced with an explicit truncation message; any other finishReason lets the real parse error propagate so a truncation and a genuine malformation are never conflated. finishReason=MAX_TOKENS is Gemini's documented signal for exactly this case (confirmed via Google's own generate-content/thinking docs, not just repo evidence -- the repo's own failing artifacts never capture the raw response body, only the downstream parse-failure message, so this specific run's finishReason value could not be directly read from any stored evidence). The maxOutputTokens budget question (raised to 8k in PR #3371) was deliberately left untouched: measuring real token consumption requires a successful live call, and every nightly run of this test in history (9 checked, back to 2026-07-22) has failed, so there is no successful usageMetadata sample to size a budget increase against -- raising the number without that measurement was the exact mistake that left #4072 half-fixed. Gemini does support bounding thinking separately from the total budget (thinkingConfig.thinkingBudget on 2.5-series models, thinkingConfig.thinkingLevel on 3-series), which is a more targeted lever than a bigger maxOutputTokens, but sizing it also needs a measured baseline this session could not obtain.
