# GitHub planning and tracking

Use only when issue or PR tracking is useful to the requested delivery.

1. Read the target issue and linked live state before asking questions.
2. Ask only about scope or authority that cannot be derived safely.
3. Choose the simplest delivery shape: direct target, one branch/PR, or separate PRs for truly
   independent work.
4. Sequence dependencies and name the riskiest premise first.
5. Reuse an existing issue when it owns the action. Search before creating a new issue.
6. Use a tracker only for a real multi-item program whose status needs a durable index.
7. Keep issue and PR text aligned with delivered scope; close completed items promptly.

Issues, trackers, subtask tickets, planning commits, and draft PRs are coordination tools, not
mandatory defaults or implementation gates. Current repository and GitHub state outrank stale issue
line numbers and historical receipts.
